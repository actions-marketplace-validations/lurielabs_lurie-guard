# PG017: `serial` / `integer` primary key

## What it detects

A primary key column of type `serial`, `smallserial`, `integer` or `smallint` in `CREATE TABLE` (column-level or table-level `PRIMARY KEY`), or added with `ALTER TABLE ... ADD COLUMN ... PRIMARY KEY`. `bigserial` and `bigint` are not reported.

## Why it matters

`serial` is "not a true type", only shorthand for an `integer` column with a separate sequence as its default, and its range is "1 to 2147483647" ([numeric types](https://www.postgresql.org/docs/18/datatype-numeric.html)). The db-skills bad example sets the sequence to that maximum and the next insert fails with SQLSTATE `2200H`; it also shows a hand-written import (`id` 1 and 2) going in quietly and the next normal insert failing with `23505`, because the sequence never saw them. Moving to `bigint` afterwards is a type change that rewrites the table (PG011). `bigint GENERATED ALWAYS AS IDENTITY` costs 4 more bytes per row, never runs out, and refuses an explicit id unless the insert says `OVERRIDING SYSTEM VALUE` (`428C9` in the good example).

## The fix

```sql
CREATE TABLE customers (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  ...
);
```

## When it does not apply

- A small lookup table that cannot reach two billion rows (countries, statuses): suppress with that reason.
- Tables whose ids an import or a replication tool must preserve: `GENERATED BY DEFAULT AS IDENTITY` on `bigint`; the rule only reports the 4-byte types.

## Message

> `id serial PRIMARY KEY` on `customers` is a 4-byte key with a separate sequence: it stops at 2147483647 (inserts then fail with SQLSTATE `2200H`), and moving to `bigint` later rewrites the whole table. Declare it `id bigint GENERATED ALWAYS AS IDENTITY`: 4 more bytes per row, never runs out, and the SQL-standard identity refuses hand-written ids. Not needed for a small lookup table that cannot reach 2 billion rows; suppress with that reason. (PG017, [evidence](https://github.com/rafapeixer/db-skills/blob/c6eb44e9ab3b9458099b0a808ca4a2cde9f2db57/skills/pg-keys-and-types/examples/bad/test.sql#L29-L37))
