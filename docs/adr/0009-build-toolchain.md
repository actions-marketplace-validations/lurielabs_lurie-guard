# ADR 0009: Build toolchain: esbuild bundle, vitest, ESLint, `dist/` committed

Status: accepted, 2026-10-19

## Context

[ADR 0001](0001-runtime-javascript-action-with-wasm-parser.md) decided TypeScript compiled to one JavaScript bundle, run with `runs.using: node24`, with the parser's WebAssembly vendored into `dist/`. It did not name the bundler, the test runner or the linter. GitHub's guide for JavaScript actions says the action's code and its modules must be checked in (the runner does not run `npm install`) and shows `@vercel/ncc` as one way to compile them into a single file ([creating a JavaScript action](https://docs.github.com/en/actions/sharing-automations/creating-actions/creating-a-javascript-action)).

What the build has to do:

- Bundle `src/main.ts` (the action) and `src/cli.ts` (the local CLI) into `dist/` with every dependency inlined, as CommonJS so the `.wasm` files can be located relative to the bundle with `__dirname`.
- Copy the WebAssembly files (`libpg-query.wasm`, `web-tree-sitter.wasm`, `tree-sitter-ruby.wasm`, `tree-sitter-python.wasm`) next to the bundle; the emscripten loaders read them from disk at run time.
- Produce an index of `rules/pg/*/rule.ts` so the engine does not scan the filesystem at run time.
- Run the unit tests, the fixture harness, the snapshot tests and the end-to-end test without a network.
- Be checked in CI: `dist/` must match a fresh build, so a PR cannot ship a bundle that differs from the source.

## Decision

- **esbuild** ([esbuild.github.io](https://esbuild.github.io/)) bundles both entries with `--bundle --platform=node --target=node24 --format=cjs`. A small build script (`scripts/build.mjs`) runs esbuild, copies the `.wasm` files and writes `dist/` deterministically (no timestamps, sorted rule index). `dist/` is committed; CI rebuilds and runs `git diff --exit-code dist/`.
- **vitest** ([vitest.dev](https://vitest.dev/)) runs every `rule.test.ts` and the tests under `src/`, with snapshots for the reporters. It runs TypeScript directly, so the test loop does not depend on the bundle.
- **ESLint** with `typescript-eslint` in the flat config format ([eslint.org](https://eslint.org/docs/latest/use/configure/configuration-files), [typescript-eslint.io](https://typescript-eslint.io/)) and `tsc --noEmit` for the type check.
- Dependencies are pinned to exact versions in `package.json` (no `^`), and `package-lock.json` is committed.
- The rule index `src/rules-index.ts` is generated by `scripts/gen-rules-index.mjs` from the folders under `rules/`, and `validate.sh` fails when it is stale.

## Alternatives considered

- **`@vercel/ncc`**, the tool GitHub's guide shows. It would work; esbuild was chosen because the same tool bundles the CLI entry and handles the TypeScript sources without a separate compile step, and its output is reproducible without configuration. Switching is a change to one script.
- **tsc only, with `node_modules` committed.** The guide allows it; the parser's WebAssembly and the Octokit tree make it several tens of megabytes. Rejected.
- **A test runner inside the bundle (node:test).** Possible, but the fixture harness and the snapshot tests are simpler with vitest's TypeScript support and snapshot files.

## Consequences

- `npm run build` is deterministic; two builds of the same commit produce the same `dist/`. The CI check enforces it.
- The `.wasm` files are plain files in `dist/`; the action's size is the bundle plus about 4.5 MB of WebAssembly, inside the 10 MB budget.
- Contributors need Node 24 and `npm ci`; nothing else.
